section: Fixed
---

- **pyright now actually receives the project's venv interpreter, so imports from `.venv` resolve** — `detectPythonVenv` found the venv correctly and `PythonServer.spawn` then put it at the top level of the initialization blob, as `{ pythonPath, openFilesOnly }`. That blob is also what pi-lens answers `workspace/configuration` from, and `resolveConfigurationSection` resolves each requested dot-path against it, returning null when the path is absent. Verified against a real pyright 1.1.408: it requests exactly three sections — `python`, `python.analysis`, `pyright` — reads the interpreter from `python.pythonPath`, and does **not** read `initializationOptions` for it at all. So section `python` resolved to null, the detected venv was discarded, pyright fell back to the system interpreter, and every library installed in the venv came back as `Import "x" could not be resolved`. The blob is now nested under `python`, and the dead top-level `openFilesOnly` key is replaced by pyright's real spelling, `python.analysis.diagnosticMode: "openFilesOnly"` — the same intent the old key expressed and pyright's current default, so a documented behavior stops being a no-op.
  - `detectPythonVenv` also walks a bounded number of directories above the LSP root instead of probing the root alone. `PythonServer.root` is a nearest-marker root, so in a monorepo it lands on the package directory owning `pyproject.toml` while the repo's single `.venv` sits further up — an entirely ordinary layout that used to report "no venv". The walk stops before the home directory, so a stray `~/.venv` is never adopted as a project's environment.
